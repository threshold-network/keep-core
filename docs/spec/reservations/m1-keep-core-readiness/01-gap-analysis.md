# Gap Analysis: keep-core M1 Reservation Readiness

## Summary
M1 is decided variant B scope: **creation, custody and re-anchor only** — redemption, dissolution, renewal and the watchtower veto are M2 and their Bridge-side code is absent from M1 by design, not deployed-and-gated (`feature-spec.md:9-15`, `milestone-inventory.md:7`, `roadmap.md` §0.1-0.2). keep-core's PR #4274 declares the full `ReservationActionType` enum (redemption/dissolution included) only because the storage/enum-positional rule requires every variant to keep its numeric position (`milestone-inventory.md` rule #5) — this is expected, not partial redemption/dissolution support. Findings below are scoped strictly to acceptance, re-anchor, action-timeout, and stranding — the four M1-reachable paths (`roadmap.md` §0.2). Out-of-scope code (redemption/dissolution executor absence, unenforced watchtower delay) is listed in `## Out of M1 scope` for audit-trail completeness, not as gaps.

- **Blocker:** 0 (2 found and resolved this session; see resolved rows below)
- **Major:** 1 (2 found and resolved this session, 1 new gap found this session; see rows below)
- **Minor:** 7 (2 resolved, 5 open/tracked)

*Verified at keep-core `reservations-epic` @ `f66f11240` (2026-09-28).*

## Major

| Gap | Severity | Evidence | Spec/PR ref |
| :--- | :--- | :--- | :--- |
| Protobuf marshaling was unimplemented (JSON-only) | Resolved (was Major) | `pkg/tbtc/reservation.go`'s four `CoordinationProposal` types (including the two M1-scoped `ReservationAnchorProposal`/`ReservationReanchorProposal`) previously carried `TODO: Switch to protobuf-based marshaling` and marshaled as JSON. | Re-anchor SPV proof was never submitted — generic proof-loop signature couldn't carry `(reservationKey, requestNonce)` | Resolved (was Major) | The re-anchor proposal/trigger path was never the gap: `ReservationReanchorTask` is registered in `tbtcpg.NewProposalGenerator` (`pkg/tbtcpg/tbtcpg.go:91`) and its `Run` already checked `StateMovingFunds` (`pkg/tbtcpg/reservation_reanchor.go:65-83`) — proposals were generated and broadcast. The real gap was SPV-side: `pkg/maintainer/spv/spv.go`'s generic `unprovenTransactionsGetter`/`transactionProofSubmitter` signatures carry only a Bitcoin transaction hash, so the `ActionReservationReanchor` proof-loop entry had no way to supply the `(reservationKey, requestNonce)` pair `SubmitReservationReanchorProof` needs. Fixed: `pkg/maintainer/spv/reservation_reanchor_proof.go` now implements a real getter/submitter pair — `submitReservationReanchorProof` discovers the still-pending re-anchor via `ReservationReanchorRequested` events matched against `ReservationByAnchorUtxo`, then `submitReservationActionProof` re-derives the key/nonce pair and calls the exported `SubmitReservationReanchorProof` chain binding. | Resolved via PR [#4276](https://github.com/threshold-network/keep-core/pull/4276) |
| Stranding coverage gap for `Closing`-past-`dissolutionEligibleAt` wallets — the client has no trigger for this one on-chain-eligible stranding precondition | Major | On-chain, `Reservation.sol notifyReservationStranded` (`9f8f5ef1`, ~1090-1114) accepts a stranding notification when the wallet is `Terminated`, OR `Closed`, OR (`Closing` AND `block.timestamp >= dissolutionEligibleAt`) — three distinct eligible states. keep-core's client-side triggers for this call are: the `OnWalletClosed` subscription (`reservation_wiring.go:612-651`, which per its own chain-interface doc comment at `pkg/tbtc/chain.go:259-261` "occurs when the wallet is closed **or terminated**"), the stranding startup scan (`reservation_wiring.go:594-607`), and `drainStrandingRechecks` (`reservation_action_timeout_watch.go:666-713`). All three gate identically: `if wallet.State != tbtc.StateClosed && wallet.State != tbtc.StateTerminated { continue }` (`reservation_wiring.go:594`, mirrored at `reservation_action_timeout_watch.go:694`) — so `Terminated` and `Closed` are both covered, but none of the three ever re-checks a wallet sitting in `StateClosing`. The on-chain-eligible `Closing`-past-`dissolutionEligibleAt` path therefore has zero automated client trigger; it is only reachable via a manual/permissionless `notifyReservationStranded` call from an off-client operator. This compounds with a second, related gap: `ReservationReanchorTask` (the automated remedy that would normally clear a reservation off a closing wallet before this path is ever needed) only fires for source wallet state `StateMovingFunds` (`pkg/tbtcpg/reservation_reanchor.go:139`), not `StateClosing`, even though `requestReservationReanchor` accepts both source states on-chain (D-9, confirmed in `../m1-tbtc-v2-readiness/01-gap-analysis.md`). A reservation stuck under a `Closing` wallet therefore has no automated remedy of either kind (re-anchor or stranding) from keep-core until the wallet eventually reaches `Terminated`/`Closed` through some other path. Not launch-blocking (a permissionless caller can always invoke `notifyReservationStranded` manually, and this is a secondary safety valve, not the primary re-anchor-away remedy), but a real automation/liveness gap worth closing before relying on keep-core's watchers as the sole operational backstop. | `Reservation.sol` `notifyReservationStranded` (`9f8f5ef1`); `reservation_wiring.go:594,612-651`; `reservation_action_timeout_watch.go:694-696`; `pkg/tbtcpg/reservation_reanchor.go:139` |

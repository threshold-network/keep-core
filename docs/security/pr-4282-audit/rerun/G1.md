### Confirmed or Plausible Medium-or-higher detail

#### G1-R3 / G1-R5: The moved funds sweep path has no P2 protocol-minimum floor gate
- Path: `pkg/tbtc/moved_funds_sweep.go:136` (execute) and `:283` (ValidateMovedFundsSweepProposal).
- Evidence: the P2 commit `a83ba04ef` added `rejectIfProposedWalletTxFeeBelowProtocolMin` to five paths (deposit sweep, moving funds, redemption, reservation anchor, reservation re-anchor). `ValidateMovedFundsSweepProposal` was left calling only `chain.ValidateMovedFundsSweepProposal` (the on-chain view, which enforces `fee > 0` and `fee <= cap` but no relay floor). A below-protocol sweep fee on the moved-funds path is therefore co-signed by every follower and jams the moving-funds wallet until the on-chain sweep timeout. This is a coverage gap in the P2 fix, distinct from the five gated paths.
- Second check: the moved funds sweep file is unchanged in the PR (`git diff a7ac8989 49c4df13d` is empty for it) and identical on `origin/dev` and the merged head; the path never had the warn-only check that P2 turned into a reject, and it never got the reservation RPC deadlines. The gaps are real, but they are properties of a path the PR does not touch, so they route outside this record. Recorded here because the first audit's P2 package claimed to cover every wallet-tx path.

#### G1-R4: The moved funds sweep execute has no RPC deadline
- Path: `pkg/tbtc/moved_funds_sweep.go:154` and `:143`.
- Evidence: `execute` calls `ValidateMovedFundsSweepProposal`, `assembleMovedFundsSweepUtxo` and `DetermineWalletMainUtxo` on the connection's parent context. The P4 deadline work wrapped only the reservation execute paths (`reservation.go` is the sole tbtc file with `rpcCallWithTimeout`), so a hung Electrum endpoint holds the per-wallet dispatcher lock for the whole execute. G1-F11 is closed for the reservation paths only.

#### G1-R6: The new bare-floor helper multiplies two int64 values before promoting
- Path: `pkg/tbtc/proposal_fee_check.go:244` (and `:191`).
- Evidence: `warnIfProposedWalletTxFeeBelowBareFloor` built `big.NewInt(floor * vsize)` from an int64 product. An operator floor above `MaxInt64/vsize` wrapped the product negative and hid the warning (operator self-inflicted, warning only).
- Fix: `95a3a7c64` uses a big.Int product. `TestWarnIfProposedWalletTxFeeBelowBareFloor_LargeFloorDoesNotWrap` failed before the fix and passes after it.

#### G1-R7: A permissionless caller reserves a live target's full re-anchor capacity
- Path: `pkg/tbtcpg/reservation_reanchor.go` `reanchorTargetSearch.find`.
- Evidence: an unprivileged caller with many source wallets can issue re-anchor requests that all target one Live wallet and hold its full count/amount headroom until each pending request times out, starving that wallet's own re-anchors. Griefing, not a fund move; bounded by the request timeout and candidate count.
- Note: `pkg/tbtcpg/reservation_reanchor.go` is new in the PR, so the file is PR code; the capacity hold itself is decided on chain. `Reservation.requestReservationReanchor` (tbtc-v2 `eec999aad` Reservation.sol:723-800) lets anyone re-anchor a reservation whose source wallet is MovingFunds or Closing to any Live target of the caller's choice, and the target capacity is held until the action times out. The Go `find` only picks targets for honest re-anchors and cannot stop third-party requests, so this is an on-chain design note, not a keep-core defect.

#### G1-R11: A timed-out reservation RPC read parks an unbounded goroutine
- Path: `pkg/tbtc/reservation.go` `rpcCallWithTimeout` (`:36-60`).
- Evidence: the P4 helper spawns `go func() { val, err := call(); resultCh <- result{val, err} }()` (a size-1 channel) and waits `reservationRPCRequestTimeout`; on timeout the spawned goroutine stays parked until the Electrum retry budget ends - one parked goroutine per timed-out read, memory-bounded, liveness only.
- Fix: the batch-2 fix `106322562` replaced a first attempt that keyed an in-flight registry by method label (which let one wallet's read reject the same read for every other wallet, and one hung call block that method for all wallets) with a global 64-slot bound held until the backend answers. `TestRerun_G1R11_RPCCallsParkedAfterTimeoutAreBounded` and `TestRerun_G1R11_IndependentRPCCallsRunConcurrently` both fail on the first attempt; the bound test fails on the pre-fix code.

#### G1-R17 / G1-R20: Disputed (informational)
- G1-R17 (`pkg/tbtc/deposit_sweep.go:692-715,754-762`): `checkSweepFeeFloor`'s size estimator uses fixed dummy script parameters with a deterministic virtual size that never fails at runtime; `MinWalletTxSatPerVByteFee` is positive by config validation; the on-chain `WalletProposalValidator` validates the proposal. No code change.
- G1-R20 (`pkg/tbtcpg/reservation_reanchor.go:394-400,1174,1256-1267`): candidate selection in `addCandidateIfLive` queries on-chain state and validates `wallet.State == tbtc.StateLive` for both cached and event-discovered wallets; on the resume path `ValidateReservationReanchorProposal` calls the on-chain `WalletProposalValidator` which verifies the target is `Live`. No code change.

#### G1-R18 / G1-R19 / G1-R21 / G1-R22 / G1-R23: held, no change
- G1-R18: the PR-added reservation unmarshal caps fee bytes at 8, so `Int64()` can no longer wrap for on-network proposals; only a programmatically-set out-of-range `ReanchorTxFee` reaches it.
- G1-R19 (leader tolerance 0 vs follower tolerance): decision D9 keeps a strict leader and a lenient follower; giving the leader the follower tolerance would let it propose targets a lagging follower rejects. The worker change was reverted (`4a9ad6bfb`).
- G1-R21: trying the next candidate after a cap revert is intended and tested (`TestReservationReanchorTask_CapRevertLeadsToNextCandidate`).
- G1-R22: the parameters are governance-set, and the same sum in Solidity 0.8 checked arithmetic reverts at request time, so a re-anchor request with a wrapping sum cannot exist; the worker's test passed on the old code because the search had no Live target. Reverted (`4a9ad6bfb`).
- G1-R23: the fee estimator rejects a non-positive rate before the product exists, so a negative total fee cannot reach the guard; the worker's test hit the estimator error, not the new guard. Reverted (`ab19c5070`).

#### G1-R28 / G1-R29: intentional design and a partial fix
- G1-R28: the activation map ships empty so reservation actions are gated off on every public network until an operator adds an explicit entry; the doc comment says so. Intentional staged rollout.
- G1-R29: the reveal-lookup band centers on a host-clock `now` at `pkg/tbtc/deposit_reveal_lookup.go:113`; a band miss only widens the scan, it cannot exclude a valid reveal. The batch-2 fix `d92646e8f` centered the lookup on chain head time; `TestRerun_G1R29_RevealLookupCentersOnChainHeadTime` fails with the host clock (window starts at [222000, 231999] and misses block 299990).

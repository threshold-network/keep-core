### Detailed findings

#### G2-R1: Stale deposit tick wipes resume cursor before reading it
- Path: `pkg/maintainer/spv/reservation_stale_deposit_watch.go:593`
- Evidence: `pollTick` sets `rsdw.checkCursor = ""` at line 593 immediately before calling `nextCheckOrder()` at line 594. `nextCheckOrder()` reads `rsdw.checkCursor` (line 659), which is always empty. As a result, `nextCheckOrder()` returns all keys starting from index 0 on every tick. When the 50-check budget (`reservationStaleDepositMaxChecksPerTick`) is reached at line 606, `rsdw.checkCursor` is updated to the 50th key, but the next tick's line 593 wipes it back to `""` before `nextCheckOrder()` is invoked. Keys at index 51+ are starved and never checked.
- Fix: Remove `rsdw.checkCursor = ""` at line 593 so the cursor persists across ticks. Landed in `cb0e62c29` with `TestRerun_G2_R1_StaleDepositCursorPreservedAcrossTicks`.

#### G2-R2: Unbounded chain-head read fanout in stale deposit watcher
- Path: `pkg/maintainer/spv/reservation_stale_deposit_watch.go:272`
- Evidence: `CheckStaleReservedDeposit` executes `reservationChainHeadTime(rsdw.spvChain)` on every invocation, issuing an RPC call (`GetLatestBlockTimestamp`). In a tick checking 50 deposits, 50 separate head-time reads are issued.
- Fix: Read the chain head timestamp once at the beginning of `pollTick` and pass it into `CheckStaleReservedDeposit`. Landed in `cb0e62c29` with `TestRerun_G2_R2_StaleDepositWatcherSingleHeadTimePerTick`.

#### G2-R3: Re-anchor candidate search reads source wallet history instead of target
- Path: `pkg/maintainer/spv/reservation_proof_loop.go:1029-1035`
- Scan evidence: `proveReservationReanchorActions` calls `walletTransactionsForProof` with `event.SourceWalletPublicKeyHash`. In a cross-wallet re-anchor (where source != target), the 1-in-1-out Bitcoin transaction spends the source anchor UTXO and sends output funds to the target wallet script. Electrum `blockchain.scripthash.get_history` indexes transactions by output script, so the re-anchor transaction appears only in the target wallet's history, not the source's. The candidate lookup `candidateTransactions[*reservation.AnchorUtxo.Outpoint]` is empty, `outcome` is `NoMatch`, and the generation is backed off and never proved by this maintainer.
- Second check: **false positive.** `walletTransactionsForProof` reads `GetTxHashesForPublicKeyHash`, which uses Electrum `blockchain.scripthash.get_history` (`pkg/bitcoin/electrum/electrum.go:806-818`). That protocol call returns every transaction that funds *or spends* the script. A re-anchor transaction spends the source anchor output, which pays to the source wallet script, so it does appear in the source wallet's history. No change.

#### G2-R4: Zero wallet-reservation count from single RPC read trusted as absence of work
- Path: `pkg/chain/ethereum/tbtc.go:1317`
- Scan evidence: `WalletReservations` executes `count, err := tc.reservationRouter.WalletReservationsCount(...)` and returns `nil, nil` if `count == 0`. A lagging or malfunctioning RPC node returning 0 causes the maintainer to skip the stranding scan for that wallet entirely.
- Second check: **disputed (design).** `WalletReservationsCount` is a direct contract storage counter on `ReservationRouter.sol`, read from the same node as every other call in the pass; returning `nil, nil` on zero without scanning event logs is the intended design and avoids unnecessary log queries. No change.

#### G2-R5: First lying registration-block read cached permanently as scan lower bound
- Path: `pkg/chain/ethereum/tbtc.go:1423`
- Scan evidence: `earliestWalletRegistrationBlock` resolves the registration block and stores any non-zero result in `walletRegistrationBlockCache`. If an RPC glitch returns an artificially high block number, the corrupted value stays cached for the process lifetime.
- Second check: **disputed (design).** `NewWalletRegistered` is an immutable historical event; caching the resolved registration block avoids repeating full-chain log queries on subsequent lookups, and the cache is process-scoped. No change.

#### G2-R6: pollTick budget counter tests host clock instead of chain head
- Path: `pkg/maintainer/spv/reservation_stale_deposit_watch.go:600`
- Evidence: `pollTick` checks `if now >= tracked.refundDeadline` using the host wall clock `now`, but `CheckStaleReservedDeposit` evaluates `headNow <= deadline` against the chain head timestamp. When the host clock lags behind the chain head, `now >= tracked.refundDeadline` evaluates to false, skipping the budget decrement (`checksLeft--`). The loop then checks all tracked deposits without decrementing the budget, executing up to 4 chain reads per deposit (200 deposits = 800 reads, 4x above the 200-read budget cap).
- Fix: Evaluate the `pollTick` budget condition against chain head time `headNow`. Landed in `cb0e62c29` with `TestRerun_G2_R6_StaleDepositPollTickBudgetUsesChainHeadTime`.

#### G2-R7: Zero dissolution-eligible timestamp is read as never eligible on Closing wallets
- Path: `pkg/maintainer/spv/reservation_stranding_watch.go:257-258`
- Scan evidence: On Closing wallets, `checkStranding` enforces `if requireDissolutionEligible && (reservation.DissolutionEligibleAt == 0 || uint64(headTime.Unix()) < uint64(reservation.DissolutionEligibleAt)) { recheck = true; continue }`. For term-less reservations (`DissolutionEligibleAt == 0`), the Go code treats 0 as never eligible and perpetually requeues the wallet every tick. On-chain, `Reservation.sol:1091` enforces `block.timestamp >= reservation.dissolutionEligibleAt`, which is always true for 0.
- Second check: **disputed (unreachable).** On tbtc-v2 `eec999aad` a reservation first becomes Active only in `settleAcceptance` (`ReservationProofs.sol:557-570`), which writes `dissolutionEligibleAt = expiresAt + dissolutionDelay`, where `expiresAt = block.timestamp + termSeconds` > 0. The two other Active writes (`Reservation.sol:903` re-anchor timeout, `ReservationProofs.sol:808` re-anchor settle) keep the field. `DissolutionEligibleAt == 0` is therefore unreachable for an Active reservation, and the `== 0` clause only fails closed for that state. No change.

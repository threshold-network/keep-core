### Liveness property: reclassified

An earlier version of this report called the liveness failure "expected" without checking it. The property was stale in the same way as the caps property. It asked whether another Live wallet had free per-wallet capacity (`hasTargetWithCapacity`, reason `NO_TARGET_WITH_CAPACITY`). A privileged hand-off off a retiring source skips the target's per-wallet caps, so a full target is not a block. The five-call sequences Medusa found (reveal, accept, retire, prove, lower the caps) were this stale case: they only lowered the caps below the position, which the library ignores for a hand-off.

What changed:

- The property now asks for a Live target other than the source (`NO_LIVE_TARGET`) and an anchor above the re-anchor floor (`ANCHOR_AT_REANCHOR_FLOOR`). Two properties report the two reasons separately.
- A new action `tryHandOff` makes the owner request a hand-off whenever the rules say it is possible (Active position, MovingFunds or Closing source, Live target, anchor above the floor). `property_aPossibleHandOffIsNeverRefused` fails if the library ever refuses one. A canary property that must fail proves `tryHandOff` succeeds in the campaign.
- Forge tests pin the behavior: an owner hand-off onto a full target works and a third party's does not; hand-offs pile onto one wallet beyond its per-wallet cap (three positions on one wallet with a cap of one) while the global active count and the accounting properties hold; the property fires when no other wallet is Live.

This version also reported "a hand-off was never refused". That statement was incomplete; the next section corrects it.

### Liveness harness: two defects found in review, fixed in `b622b4bc0`

1. **Masking.** Both split properties read `firstStuckPosition()`, which returns only the first stuck key. A floor-stuck position early in the key list hides a no-live-target position, so "the floor property passed" did not show that the floor case was unreachable. Each property now scans every key (`anyPositionStuckFor`). A forge test (`test_oneStuckReasonDoesNotHideTheOther`) puts a floor-stuck position at key 0 and a no-live-target position at key 1, and both properties fail.
2. **Cooldown refusal.** A fresh 10-minute Medusa run (about 187,000 calls) on the scanning version failed `property_aPossibleHandOffIsNeverRefused` with a 44-call sequence; the raw log is `medusa-raw/liveness-scan-10min-cooldown-refusal.log.txt`. The refusal was "Reanchor cooldown in effect": after `notifyReservationActionTimeout`, the library refuses a re-anchor from the owner until `reanchorCooldownUntil`. The cooldown test in `Reservation.sol` uses the governance-discriminated `privileged` flag, not the owner or maintainer status, so only governance skips it. The cooldown always ends, and the liveness property already ignored it, but `tryHandOff` did not. Why the first version never failed was not checked; most likely its carried-over corpus never reached a timeout followed by an owner hand-off. `tryHandOff` now skips attempts inside the cooldown. `test_tryHandOffWaitsOutTheCooldownAfterATimeout` pins that the library refuses the owner inside the cooldown, the action stays out of it, and a hand-off succeeds once it ends. This is a gap in the model, not a contract defect. The shrunk sequence was not replayed as a forge test; that test covers the same refusal reason.

Foundry after both fixes: 24 tests pass (13 invariant and fire tests, 11 liveness tests).

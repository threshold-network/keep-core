## Conflict and its resolution

`git merge-tree --write-tree` reported exactly one conflict:
`solidity/test/bridge/Bridge.ReservationStrandingLibrary.test.ts`, at the `eslint-disable`
block at the top of the file.

- The line's side has `@typescript-eslint/no-unused-expressions`.
- The PR's side has `no-bitwise` and `@typescript-eslint/no-non-null-assertion`.

The file needs all three: it uses chai `.to.be.true`-style assertions, and it carries 34
bitwise operators and 63 non-null assertions. The conflict was resolved as the union of the
two directive sets. No test logic changed. The repository Prettier reports the file
unchanged.

## Deployed bytecode

Hardhat appends CBOR metadata that embeds a hash of the compilation inputs, and the
configuration does not set `metadata.bytecodeHash` to `none`. Moving a comment therefore
changes the metadata hash of every artifact in the compilation, not only the contract that
changed.

Compiled at `c5cb387cf` and at `36edb21d5`, same configuration:

| Contract | Deployed size | First differing byte | Code before the metadata tail |
|---|---|---|---|
| Bridge | 23568 | byte 23525 of 23568 | identical |
| ReservationRouter | 13287 | byte 13244 of 13287 | identical |
| Reservation | 17835 | byte 17792 of 17835 | identical |
| ReservationVault | 7010 | byte 6967 of 7010 | identical |
| WalletProposalValidator | 21210 | byte 21167 of 21210 | identical |

All five differ only in the last 43 bytes, the appended CBOR metadata. The executable code
is byte-identical and the deployed sizes are unchanged. Nothing on chain reads those bytes,
and any artifact recompiled from the merged source is self-consistent. The Sepolia rehearsal
artifact records addresses and ABIs, not bytecode, so it is not invalidated; the keep-core
drift check compares ABIs, so it is not either.

### The reserve-gate property

Before this run no property asserted the acceptance gate `active <= (Live wallets - reserve) *
per-wallet count cap` in `Reservation.reserveAcceptanceCapacity`. The reserve was fuzzed, so the
gate ran, but only the other accounting properties could notice a side effect of it.
a fuzz-tooling branch @ `fc6b7fbc7` (a test-only commit on `8a2cf699e`, pushed to
`tlabs-security` only) adds `property_reserveGateHoldsAfterEveryAcceptance`.

- It is checked right after each successful acceptance request, the one step the gate guards.
  It is not a global invariant: governance may raise the reserve, or a wallet may retire, which
  legitimately leaves the open count above the bound until positions close.
- `ReservationHarnessState.reserveGate()` exposes the Live wallet count, the reserve and the
  per-wallet count cap.
- Two tests: `test_reserveGatePropertyFires` (a mocked view makes the post-request check fail) and
  `test_reserveGateStopsAcceptanceAtTheBudgetAndHolds` (4 Live wallets, reserve 1, one position
  per wallet: three requests succeed, the fourth reverts with "Hand-off reserve exceeded", and
  the property holds).
- Red check, run in a scratch worktree on `fizz-v2`: with the gate `require` neutralised
  (`true || ...`), the invariant failed on the "reserve gate" assertion, the new budget test
  failed with "next call did not revert as expected", and the existing
  `test_reserveKeepsAFreeTargetWhenEveryOtherWalletIsFull` failed with `reserve admits 3: 4 != 3`.
  The edit was then reverted, and `git diff -- solidity/contracts` against `HEAD` is empty.
- On `d47be35eb` the property passed in the 10 of 10 Medusa accounting run above and in the
  `ci` invariant run (256 runs, 25,600 calls).

### The harness revision matters

Foundry and Medusa were first run here with a fuzz-tooling branch @ `e001440d6`. That
revision predates the hand-off reserve. Two failures appeared, and both are already recorded
as stale-property issues, not contract bugs:

- `test_firesWhenEveryLiveWalletIsFull` failed with `accepted: 3 != 4`. The reserve stops the
  fourth acceptance; raising the reserve to 2 gives `accepted: 2 != 3`, so the acceptance gate
  is `(Live - reserve) * perWallet`. The 2026-10-14 record replaced this test with
  `test_reserveKeepsAFreeTargetWhenEveryOtherWalletIsFull`.
- `property_capsHoldAfterEveryRequest` failed. The cause is the property, not the contract: a
  privileged re-anchor off a non-Live source skips the target's per-wallet caps on purpose,
  and the newer harness exempts exactly that case (`exemptHandoff`).

With a fuzz-tooling branch @ `8a2cf699e`, the revision the 2026-10-14 record cites
and which contains `7d5d7add8` and the liveness harness `b622b4bc0`, both suites were clean;
`fc6b7fbc7` adds one property on top of it (previous subsection). The stale run is recorded
here so no one re-derives those two known results. Its harness files in `rec3-wt` were
overwritten by the later copies; the stale-run Medusa corpora and logs are kept in
`rec3-wt/solidity/cache_forge/` under names ending `.stale-e001440d6`. The copies of the
harness in `rec3-wt/solidity/test-foundry/reservations/` and `solidity/medusa-reservations*.json`
